# 5C.3 - Rotation Banner

## Install/upgrade

Stop Starpoint and back up `var/database/world-flipper.db`, then extract the overlay over the project root and run `pnpm build`. Migration 11 runs automatically on the next server/CLI startup. It copies the previous generated rows to `runtime_gacha_banners_v1_backup` and `admin_gacha_overrides_v1_backup`, then regenerates the new six-month schedule.

The first startup records each existing player's current season without wiping their roster. The character/party seasonal reset runs only when that recorded player later crosses a real six-month boundary.

## Calendar formula

For a Gregorian month with `D` days:

```text
q = floor(D / 7)
r = D mod 7

run[0 .. q-2] = 7 days
run[q-1]      = 7 + r days
```

Therefore the final run is 7-10 days for all real months and always satisfies the 13-day hard limit. A season contains six consecutive calendar months. All boundaries use `timezoneOffsetMinutes` from `content/live/gacha-rotation.json`.

Rerun has an explicit first window from Season Day 21 through the end of that month, then follows the normal monthly windows. Meteor Fes uses `[lastDay-13, lastDay-7)` and `[lastDay-6, nextMonthDay1)`. Anniversary is the second of those windows.

## Deterministic materialization

Random ordering uses:

```text
u = uint32_be(SHA256(seed + season + cycle + slot + unitId)[0..3]) / 2^32
```

Candidates are sorted by `u`, then ID. The selected pool, featured IDs, rates and dates are stored in `runtime_gacha_banners`; an existing row is never regenerated after restart.

`season_unit_release` is keyed by `(season_number, content_type, unit_id)`. At a new season only Base characters are seeded as released; every other character begins unreleased again. Equipment eligibility is seeded each season but player equipment ownership is never wiped.

## Manual override, automatic fallback

Edit `content/live/gacha-rotation-overrides.json`:

```json
{
  "runs": {
    "2:8:new": {
      "featuredIds": [151006, 141001, 141002]
    },
    "2:9:weapon": {
      "featuredIds": [5020030],
      "poolIds": [5020030, 5010028, 5010061, 5020008]
    }
  }
}
```

The key is `season:cycle:slot`. Omit `featuredIds` to let Starpoint select deterministically. Omit `poolIds` to let Starpoint construct the eligible pool. Overrides are only read before a run is materialized; delete/edit the persisted run through the admin page if it already exists.

## Manual Seasonal banners

Edit `content/live/gacha-seasonal-banners.json`. Unlike New Faces/Rerun, these entries do not use a procedural pool generator:

```json
{
  "banners": [
    {
      "id": "summer-2026",
      "shellGachaId": 156,
      "startAt": "2026-05-01T00:00:00+07:00",
      "endAt": "2026-05-08T00:00:00+07:00",
      "poolIds": [151006, 141001, 141002, 131001, 121001, 111001],
      "featuredRatesPercent": {
        "151006": 1.5,
        "141001": 2.5
      },
      "rankRatesPercent": {
        "5": 7.5,
        "4": 25,
        "3": 67.5
      },
      "multiGuaranteeMinimumRank": 5
    }
  ]
}
```

`rankRatesPercent` must total 100. Featured rates are exact percentages; Starpoint distributes each rarity's remaining rate equally among its non-featured entries. Each rarity must have at least one entry. `multiGuaranteeMinimumRank` is optional (`4` or `5`). Featured units are marked released in that season when the banner begins.

Do not overlap two logical banners that share the same `shellGachaId`: the native request only carries that numeric ID, so the server cannot distinguish two simultaneous cards using one shell.

Normal and Meteor rank rates are configured in `content/live/gacha-rotation.json` under `ratePolicies`. The default policies are `[5, 25, 70]` and `[7.5, 25, 67.5]` (ordered ★5/★4/★3).

## Commands

Stop the server before modifying the SQLite database.

```powershell
pnpm gacha:rotate
pnpm gacha:rotate -- --at 2026-09-07T12:00:00+07:00
pnpm gacha:probability
```

The database migration runs automatically at server/CLI startup.

## Native EoS client limit

The final EN client master has only three simultaneous shells at the frozen protocol time: `157`, `155`, and `5033`. Starpoint materializes all logical Base/New/Rerun/Elemental/Weapon/Meteor/Anniversary runs and exposes them in the admin/probability API, but `clientVisibleSlots` advertises only the three safe shells to the unpatched game client. Showing four or five distinct native cards simultaneously requires a client master patch; inventing server IDs causes “Does not appear to be available”.
